# Supabase migration: `campaign_trigger`

The dashboard's new "Triggers" wizard step (between **Active Sensing** and **Confirm Configuration**) reads from and writes to a Postgres table that does not yet exist on the self-hosted Supabase backend. Apply the migration below before using the feature, then regenerate `src/lib/schema.ts`.

## 1. Apply the SQL

Run this against the self-hosted Supabase database (e.g. via Supabase Studio's SQL editor, or `psql` against the Postgres container):

```sql
create table if not exists public.campaign_trigger (
    id           bigint generated by default as identity primary key,
    campaign_id  bigint not null references public.campaigns(id) on delete cascade,
    name         text   not null default '',
    condition    jsonb  not null,
    action       jsonb  not null
);

create index if not exists campaign_trigger_campaign_id_idx
    on public.campaign_trigger (campaign_id);
```

Notes:

- `condition` stores the boolean tree (`detection`/`and`/`or`/`not` nodes) defined by `TriggerCondition` in `src/types/trigger.ts`. AND, OR and NOT can be nested arbitrarily — the column is `jsonb` so the schema does not constrain depth.
- `action` stores **a JSON array of side-effects** — each element is one of `{ kind: "ema", survey_id: number }`, `{ kind: "watch_ema", survey_id: number }`, or `{ kind: "broadcast", action: string, targetPackage?: string, extras: BroadcastExtra[] }`. A trigger fires every action in its array. The column name stays singular for backwards compatibility, but the dashboard always writes an array. The dashboard resolves the in-memory `surveyIndex` to a real `survey.id` at save time.
- The broadcast action shape is the data carried by an Android `Intent` consumed by another app's `BroadcastReceiver`: `action` is the Intent action string the receiver's `<intent-filter>` matches on, `targetPackage` is the optional explicit-broadcast target (recommended on Android 8+), and `extras` is a list of typed key/value pairs serialized into the Intent's Bundle. `BroadcastExtra.valueType` is one of `string | int | long | boolean | float | double` — the value is always stored as a string and parsed on the Android side.
- `on delete cascade` keeps trigger rows in sync when a campaign is removed.

### One-time backfill if there are pre-existing rows

The dashboard previously stored a single action object in this column. The current code expects a JSON array. Run this once to wrap any old rows:

```sql
update public.campaign_trigger
   set action = jsonb_build_array(action)
 where jsonb_typeof(action) <> 'array';
```

The dashboard's read path (`loadActions` in `src/types/trigger.ts`) tolerates either shape, so a missed backfill won't crash old rows — they will just round-trip as a single-element array on next save.

## 2. Regenerate `src/lib/schema.ts` after future schema changes

`src/lib/schema.ts` already includes the `campaign_trigger` entry under `Database['public']['Tables']`, and `src/types/trigger.ts` derives `CampaignTrigger` from it. If you change the table later, regenerate the file using whichever command originally produced it — for example:

```sh
npx supabase gen types typescript \
    --db-url "$DATABASE_URL" \
    --schema public > src/lib/schema.ts
```

## 3. Adjust the value enums to match the Android library

`TRIGGER_SENSOR_VALUES` in `src/types/trigger.ts` is currently a placeholder:

```ts
stress:            ["low", "medium", "high"]
physical_activity: ["still", "walking", "running", "cycling", "in_vehicle"]
gesture:           ["nod", "shake", "tap"]
```

Update each list to match what the EnPULSE Android library actually emits for these classifiers. Saved triggers store the value as a plain string in `condition.value`, so changing the enum will not break already-stored rows but will hide them from the UI dropdown if their value is no longer in the list.
